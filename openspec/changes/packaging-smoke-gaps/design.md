# Design

## Context

- Compose's `packageDeb`/`packageReleaseDeb` tasks run jpackage, whose `postinst` and `prerm` (both `set -e`) run `xdg-desktop-menu install|uninstall /opt/shogunai/lib/shogunai-ShogunAi.desktop`. The desktop entry exists because the app has a custom icon. `xdg-desktop-menu` exits 3 ("No writable system menu directory found") when no `menus` folder under `XDG_CONFIG_DIRS` (default `/etc/xdg`) is writable. Reproduced on `ubuntu:24.04` with the `0.0.0` release candidate's `.deb`: install leaves `half-configured`, and `apt-get remove` fails in `prerm` too.
- jpackage takes custom `postinst`/`prerm` templates from `--resource-dir`, but Compose (1.12.2) passes its own `build/compose/tmp/resources` as `--resource-dir`, clears it inside the task action before running jpackage, and puts `freeArgs` before its own arguments, where jpackage keeps the last value of a repeated option. There's no supported way to give jpackage our templates.
- `smoke-linux.sh` creates `/etc/xdg/menus`, `/usr/share/applications` and `/usr/share/desktop-directories` before installing, which hides the failure.
- `release.yml` renders the Cask and the Scoop manifest with inline `sed` in the jobs that push them, after `publish-release`. `smoke-test.yml` only gets `ref`.

## Goals / Non-Goals

**Goals:**

- The `.deb` built by any Gradle Debian task, locally or in CI, installs and uninstalls without a menus folder, and still adds its menu entry on a desktop.
- The exact rendering the release pushes is installed by the smoke test, from the installers it built, before the tag and the release exist.

**Non-Goals:**

- Smoke testing winget: its manifest is generated by `winget-releaser` from the published release, so there's nothing to render beforehand; it installs the same `.msi` the smoke test checks.
- Running the app's smoke-test mode through the Cask or Scoop install: the `.dmg` and `.msi` jobs already do it on the same files; these jobs check what the manifests add (download, checksum, links, shim, shortcut, uninstall).
- An `.rpm` or other Linux formats.

## Decisions

### Rewrite the `.deb`'s maintainer scripts after jpackage

A `doLast` on every Compose jpackage task whose target format is `Deb` extracts the package (`dpkg-deb -R`), rewrites `DEBIAN/postinst` and `DEBIAN/prerm` so each line starting with `xdg-desktop-menu ` becomes `<line> || echo "ShogunAi: <warning>" >&2`, and rebuilds it in place (`dpkg-deb --root-owner-group -b`, as jpackage's `fakeroot dpkg-deb` gives root ownership). Commands run as argv through `ProcessBuilder`, inline in the action so the configuration cache doesn't capture the script object.

- The rewrite fails the build when either script has no `xdg-desktop-menu` line, so a jpackage update that changes its scripts is noticed instead of shipping unguarded ones.
- Tolerating any failure of `xdg-desktop-menu`, not only the missing folder: a menu entry is never worth a broken package, and the warning says what happened. On a desktop the command succeeds and nothing changes.
- Alternatives rejected: custom templates through `--resource-dir` (not reachable through Compose, see Context); creating `/etc/xdg/menus` from the package (a package shouldn't create a desktop's config folders on a server, and `prerm` would still depend on it); dropping the menu entry (desktop users lose it); patching in `package.yml` (local `.deb`s would keep the bug).

### Regression test: the Linux smoke test without the menus folder

`smoke-linux.sh` no longer creates the folders. It fails if `/etc/xdg/menus` exists (like its other "isn't the machine to test" checks), installs, checks `dpkg-query` reports `install ok installed`, runs the app checks as today, then `apt-get remove` and checks the package is gone. Finally it creates the three folders, installs again and checks `shogunai-ShogunAi.desktop` exists in `/usr/local/share/applications` or `/usr/share/applications`, then removes and checks the entry is in neither. `xdg-desktop-menu` installs into the first folder of `XDG_DATA_DIRS` (default `/usr/local/share:/usr/share`) whose `applications` folder is writable: a bare `ubuntu:24.04` container has no `/usr/local/share/applications`, but the GitHub runner does, so the first release candidate run found no entry under `/usr/share`. Seen failing first against the current `.deb` in an `ubuntu:24.04` container, before the Gradle fix.

### Shared render scripts

- `.github/homebrew/render-cask.sh <version> <sha256 arm64> <sha256 x64>` and `.github/scoop/render-manifest.sh <version> <sha256 msi>` read their template next to them and print the result; they fail when an argument is empty, a checksum isn't 64 hex characters, or a `@…@` placeholder is left.
- The release's `update-homebrew-cask` and `update-scoop-bucket` jobs call them instead of `sed`; their empty-checksum checks move into the scripts.

### Installing the manifests from the built installers

Both package managers verify the checksum of a file already in their download cache and skip the download, so the scripts put the built installer where each one looks for the release's URL, keeping the rendered URL untouched:

- Homebrew (`smoke-homebrew.sh`, on `macos-latest` and `macos-26-intel`, with both `.dmg` artifacts): render with `shasum -a 256` of each `.dmg`, write into a local tap (`brew tap-new --no-git`), trust it with `brew trust --tap` when that command exists (newer Homebrew refuses to load casks from untrusted taps, as the first release candidate run showed on `macos-latest`), check the cask's URL (`brew info --json=v2 --cask`) is `<release download base>/<built .dmg name for this arch>`, copy that `.dmg` to `brew --cache --cask`, `brew install --cask`, check `/Applications/ShogunAi.app` and `$(brew --prefix)/bin/shogun`, run `shogun --version` from `zsh -l` with a clean environment, `brew uninstall --cask` and check both are gone. `HOMEBREW_NO_AUTO_UPDATE=1` keeps it off the network.
- Scoop (`smoke-scoop.ps1`, on `windows-latest`): install Scoop with its official installer (`-RunAsAdmin`, as hosted runners are administrators), render with the `.msi`'s `Get-FileHash`, check the manifest's URL, ask Scoop's own `cache_path` (dot-sourcing its `lib/core.ps1`) where it caches that URL and copy the `.msi` there, `scoop install <manifest path>`, check the Start menu shortcut, run `shogun --version` through `cmd /c` with the `PATH` read again from the registry, `scoop uninstall shogunai` and check app, shim and shortcut are gone.
- The release download base is `https://github.com/<repository>/releases/download/v<version>`, passed by the workflow, so the check compares against where `publish-release` will upload.
- Alternatives rejected: rewriting the URLs to `file://` (the URL the users get would go untested); serving the files over a local HTTP server (same, plus a moving part).

### Workflows

`smoke-test.yml` gets a `version` input and two jobs, `homebrew-cask` (matrix of both macOS runners) and `scoop`, with `contents: read`, no secrets, 15-minute timeout, uploading their logs. `release.yml` and `release-candidate.yml` pass the version. `create-release` already needs `smoke-test`, so a failing manifest blocks the release.

## Risks / Trade-offs

- [Scoop renames `cache_path` or changes its cache layout] → the install then tries the real URL, which doesn't exist before publishing, and the job fails loudly; the fix is in the script.
- [Installing Scoop downloads from the network] → same as Homebrew already on the runner; a transient failure is re-run.
- [Rebuilding the `.deb` changes compression or ownership] → `dpkg-deb` uses Ubuntu's default compression and `--root-owner-group`; the smoke test installs the rebuilt file.
- [Swallowing a real `xdg-desktop-menu` error on a desktop] → the warning is printed by `apt`; the desktop-install check in the smoke test catches a regression on desktops.

## Migration Plan

No data migration. A machine left with a half-configured package by an earlier `.deb` gets out of it by installing the new one: the old `prerm upgrade` fails, dpkg then runs the new `prerm failed-upgrade`, which jpackage's template makes a no-op, and the new `postinst` tolerates the missing folder. Checked in the container during validation (install the `0.0.0` `.deb`, then the new one, then remove).
