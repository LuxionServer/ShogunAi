# Design

## Context

What a Flutter project made from the current template (`flutter create`, Kotlin DSL) looks like to ShogunAi. This was checked against Flutter's templates and `flutter_tools` sources on `master`, and against a hand-made sample repository. Flutter isn't installed on the machine where this was explored.

- **Layout.** `pubspec.yaml`, `pubspec.lock` and `lib/` at the root. Android is a self-contained Gradle build in `android/`: `settings.gradle.kts` declares `com.android.application` with `apply false` and includes the Flutter Gradle plugin from `flutter.sdk` in `local.properties`; `app/build.gradle.kts` applies the plugin; `build.gradle.kts` moves every build directory to the root `build/`. iOS is `ios/Runner.xcodeproj` plus `ios/Runner.xcworkspace`, with a tracked `Podfile.lock` when the app uses CocoaPods. `macos/`, `linux/`, `windows/` and `web/` are optional.
- **Ignored by the template and generated by Flutter.** `.dart_tool/`, `.flutter-plugins-dependencies` and `build/` at the root. In `android/`: `gradlew`, `gradlew.bat`, `gradle-wrapper.jar`, `local.properties` and `key.properties`, plus `*.jks` and `*.keystore` anywhere. In `ios/`: `Pods/`, `.symlinks/`, `Flutter/Generated.xcconfig`, `Flutter/flutter_export_environment.sh` and `Flutter/ephemeral/`.
- **`flutter pub get` regenerates almost all of it.** After resolving packages it runs `ensureReadyForPlatformSpecificTooling` (`project.dart`), which calls `updateLocalProperties` for Android, so `flutter.sdk` and `sdk.dir` are written. It also writes `Generated.xcconfig` and the export script for iOS and macOS, creates the plugin symlinks under `ios/.symlinks/plugins` (`flutter_plugins.dart`) and the ephemeral folders of the desktop platforms. `gradlew` is injected by `flutter build` and `flutter run` (`injectGradleWrapperIfNeeded`). `Pods/` comes from `pod install`, which Flutter runs itself.
- **Before the first `flutter pub get`, a fresh worktree doesn't build.** The Gradle build fails with "flutter.sdk not set in local.properties", Xcode can't find `Generated.xcconfig`, and the Dart analyzer has no package config.
- **Detection today** (`shogun stacks` on the sample) reports only Xcode (`ios/Runner.xcodeproj`, `macos/Runner.xcodeproj`). Gradle isn't found because `gradlew` and `settings.gradle.kts` aren't in the main folder. Android isn't found because `android/build.gradle.kts` doesn't mention `com.android.`; the plugin is in `android/settings.gradle.kts` and `android/app/build.gradle.kts`.
- **Mobile secrets today** report `android/local.properties` and suggest linking it. For Flutter that's wrong: every `flutter` command rewrites that file (`flutter.buildMode`, `flutter.versionName`, `flutter.versionCode` from each worktree's `pubspec.yaml`), and writing through a link changes the base repository's file. `android/key.properties`, the keystores, `google-services.json` and `GoogleService-Info.plist` are already handled. FlutterFire's `lib/firebase_options.dart`, which is often ignored and is needed to compile, isn't.

## Goals / Non-Goals

**Goals:**

- A fresh worktree of a Flutter repository builds with `flutter build` or `flutter run` and no manual step.
- Reuse the Gradle, emulator, iOS simulator, Xcode and CocoaPods providers for `android/`, `ios/` and `macos/`, adapting them where they assume the Gradle build is at the root.
- Agents run Flutter on their own worktree's device.

**Non-Goals:**

- Flutter-specific ports. `flutter run` binds its VM service, DDS and DevTools to free ports it picks, so worktrees don't collide. A repository that fixes the web server port (`--web-port`, `web_dev_config.yaml`) can already reserve one with `env` (`"FLUTTER_WEB_PORT": "${port}"`) and pass it as `--web-port`. The guide says so.
- Sharing `build/` or `.dart_tool/` between worktrees. Both hold absolute paths and incremental compiler state, and the outputs are rebuilt from caches that are already shared.
- Showing or cleaning the pub cache (`~/.pub-cache`, or `PUB_CACHE`). It is already shared by every worktree, `flutter pub get` only writes a package config that points into it, and nothing per worktree grows there. Its size could join the shared caches view later (roadmap follow-up).
- Mono-repositories of several Dart packages (pub workspaces with a non-Flutter root, Melos). They keep declaring `melos bootstrap` or their own command as a post-creation command.
- Installing Flutter or FVM versions. When `.fvmrc` names a version that isn't installed, `fvm` fails or asks, and that is reported as `flutter pub get` still needed.
- The desktop switch's design beyond a plain switch with no options.

## Decisions

**Composition, plus a thin `flutter` provider.** Flutter owns no long-lived resource of its own. Its Gradle daemons are ordinary Gradle daemons started from `<worktree>/android`, so the Gradle provider already ties them to the right worktree (the deepest worktree containing the build directory). Its Android devices are the emulator provider's: Flutter's device id for an emulator is the adb serial, `emulator-<port>`. Its iOS devices are the simulator provider's, identified by UDID. `xcodebuild`, which Flutter runs on `ios/Runner.xcworkspace`, writes DerivedData whose `WorkspacePath` is inside the worktree, so the Xcode provider attributes it as is. The pods sit next to a tracked `ios/Podfile.lock`, so CocoaPods provisioning finds them as is. What only Flutter needs is the `flutter pub get` step and the agent context, which is what the `flutter` provider adds. Alternative: one `flutter` provider that bundles device, Gradle and Xcode handling for `android/` and `ios/`. Rejected because it duplicates the pools, leases and cleanup the existing providers already own, and Flutter repositories would then behave differently from native ones for the same resources.

**`flutter pub get` runs automatically, without the repository's approval.** Ciro chose this. The command is fixed by ShogunAi and not taken from `.shogunai.json`, and it runs no repository code: packages' build hooks run at build time, not when resolving. So it falls on the same side as cloning pods rather than as post-creation commands. It runs after files are copied and pods are cloned, so `.symlinks` and the pods agree, and before the post-creation commands, so a `dart run build_runner build` declared there finds the packages resolved. Like a post-creation command, it has no timeout and can be cancelled (`command-execution`). Failures (Flutter not on `PATH`, no network for a new package, a non-zero exit) are reported and never roll back the worktree, like pods. Alternatives: gating it under the repository's approval, which `shogun hook worktree-create` always skips, so Claude Code's worktrees would never get it; or only telling the agent to run it, which leaves the first build failing for every new worktree.

**FVM through `.fvmrc`.** When the repository's root has `.fvmrc`, the command is `fvm flutter pub get`, so the version the repository pins is used and FVM creates the worktree's `.fvm/` link. Otherwise it is `flutter pub get`, with `flutter` from the `PATH` of the environment ShogunAi runs in. The agent context names the same command (`fvm flutter` or `flutter`).

**Detection of Flutter.** Flutter is detected when the main folder's `pubspec.yaml` declares the Flutter SDK as a dependency, that is, its text contains `sdk: flutter`. A pure Dart package has a `pubspec.yaml` without it and isn't a Flutter app. Only the main folder is read, like the other root-only stacks. The evidence is `pubspec.yaml`.

**Nested Gradle builds.** A direct subfolder with `settings.gradle` or `settings.gradle.kts` is a Gradle build of its own. When the main folder has neither `gradlew` nor a settings file, those subfolders are the repository's Gradle builds: the Gradle stack is detected with their settings files as evidence, the Gradle provider reads their `gradle.properties` after the root's, and the emulator provider reads `sdk.dir` from their `local.properties` after the root's. In a repository whose main folder is a Gradle build, a nested `build-logic/settings.gradle.kts` adds nothing, because the main folder already counts. The Android stack also looks for `com.android.` in `settings.gradle(.kts)` of the inspected folders, which is where Flutter's template and many plugin-management setups declare it. Alternative: a `"projectDir": "android"` option on the Gradle provider. Rejected because the layout can be found from the files, and an option would have to be repeated for the emulator.

**`local.properties` written by Flutter isn't a mobile secret.** A `local.properties` whose properties include `flutter.sdk` isn't reported or suggested, because `flutter pub get` writes it in every worktree. Its `storeFile` keys are still read, so a keystore it points to inside the repository is still reported. Alternative: suggesting `copy` instead of `link` for it. Rejected because the copy would be overwritten at once, and suggestions are `link`-only today.

**`firebase_options.dart` is Firebase configuration.** It joins the names `git ls-files --others --ignored` looks for, with the kind Firebase configuration, so an ignored `lib/firebase_options.dart` gets the `link` suggestion like `google-services.json`. `.dart_tool` joins the excluded folders.

**Agent context.** A new workflow rule, shown in `SessionStart` for repositories that declare the `flutter` provider, says:
- run `flutter pub get` (or `fvm flutter pub get`) after `pubspec.yaml` or `pubspec.lock` change;
- start the device with `shogun emulator start` or `shogun simulator start` first, then always pass it with `-d "$ANDROID_SERIAL"` or `-d "$IOS_SIMULATOR_UDID"` to `flutter run`, `flutter test integration_test` and `flutter drive`;
- never use `flutter emulators --launch`, which starts an AVD outside the pool and without read-only mode.

The device part names only the device providers the repository declares. This complements the emulator rule, which tells agents not to pass `-d` to adb. Flutter has no environment variable for the default device (`flutter_tools` doesn't read `ANDROID_SERIAL`), and with several worktrees' devices online `flutter run` without `-d` asks or picks the wrong one.

**Desktop switch after the redesign.** `SuggestedProvider` is matched exhaustively in `RepositoryConfigSection.kt` and `ProjectConfigViewModel.kt`. Adding `FLUTTER` therefore needs a label, a "Turn on" branch and a switch there. Those files belong to the UI redesign in progress in another branch, so that task group is done last and only after the redesign is merged into `develop`, rebasing first.

## Risks / Trade-offs

- [`flutter pub get` takes time or needs the network on the first worktree of a new dependency] → It runs only when the provider is declared, it's cancellable, its failure is reported and never blocks the worktree, and with a warm pub cache it resolves offline in seconds.
- [Flutter isn't on the `PATH` ShogunAi sees (the desktop app started from Finder doesn't inherit the shell's `PATH`)] → It is reported as `flutter pub get` still needed, saying the command wasn't found. The command executor already adds Homebrew's folders to `PATH`, which covers Flutter and FVM installed with Homebrew. An SDK unpacked by hand elsewhere is found from the CLI and from Claude Code's hook, which inherit the shell's `PATH`, but not always from the desktop app. Looking in more places is left as a follow-up if it turns out to matter.
- [Concurrent `flutter` commands across worktrees wait on the SDK's startup lock while it updates its artifacts] → Accepted. The wait is short and Flutter prints it.
- [A first Flutter build in a fresh worktree still runs `pod install`, because Flutter decides from a fingerprint kept in `build/`] → Accepted. Cloned pods make it fast, since nothing is downloaded or extracted. The guide explains that a "needs `pod install`" report is handled by Flutter's own build.
- [Detecting Flutter by the text `sdk: flutter` can match a comment] → Detection is only a hint with its evidence shown, like the others.
- [The desktop part waits for another branch] → The core and CLI parts are usable without it, since the provider can be declared by hand or from a terminal, and the task order makes the dependency explicit.

## Migration Plan

Nothing to migrate. Repositories that don't declare `flutter` behave as before. In repositories already using Gradle at the root, detection and the Gradle and emulator providers read the same files as before.
