# Design

## Context

`resolveProvisionedFiles` (`WorktreeCreation.kt`) turns the project's local entries (`ProjectConfig.secretFiles`) and the repository's `copy`/`link` patterns into `ProvisionedFiles(copied, linked)`, a flat list of file paths that every creation flow, `ProvisionWorktreeUseCase` and `CheckProvisionedFilesUseCase` consume. Local folders are expanded with `FileManager.listFiles`, which drops symbolic links silently. Repository patterns are expanded with `git ls-files --others --ignored -z -x <pattern>`. `applyProvisionedFiles` copies or links file by file behind `requireInsideWorktree`, falling back to a copy on `SymbolicLinksNotSupported`. Per-worktree state already lives in the worktree's Git admin folder (`git rev-parse --git-dir`), as the reserved ports do through `EnvironmentStateStore`. Provider suggestions come from `DetectRepositoryStacksUseCase` plus `suggestProviders`, shown in `shogun stacks` and in the project settings; accepting one is an unsaved edit written with the existing preview. `RepositoryConfigEdit.addCopyPatterns` already lets the app append patterns to `.shogunai.json`. See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**
- Every new behavior goes through the existing pipeline (`ProvisionedFiles`, drift check, rollback, reports), so the creation flows, `shogun provision`, the hooks and the app stay consistent.
- Old `projects.json` files load unchanged and keep copying.

**Non-Goals:**
- Removing files deleted from the base repository for exact entries, patterns or `.shogunai.json` patterns; only local folders are reconciled.
- Removing the empty folders left behind after deleting stale files.
- Rewriting keystore paths or editing the user's properties files.
- Detecting secrets of other stacks (Flutter's own layout, iOS package caches) beyond the listed file names.

## Decisions

**Mobile secrets are found with one `git ls-files` call.** `git ls-files --others --ignored -z -x local.properties -x keystore.properties -x key.properties -x '*.jks' -x '*.keystore' -x google-services.json -x GoogleService-Info.plist` in the base repository lists the untracked files with those names at any depth, which is exactly what a `link` pattern would later see. Paths under `build/`, `.gradle/`, `node_modules/`, `Pods/` and `DerivedData/` are dropped. Files already covered by the current provisioning (the result of `resolveProvisionedFiles`, so local entries, `copy`, `link` and `.worktreeinclude` all count) aren't suggested. Alternative: extend the name-only walk of `DetectRepositoryStacksUseCase`. Rejected: Firebase files usually sit deeper than one level (`app/src/debug/`), and the walk can't tell tracked from untracked files.

**The suggestion is an anchored `link` pattern.** Each secret is suggested as `/<relative path>` in `link`: secrets rotate (a new `google-services.json`, a renewed keystore) and a link keeps every worktree current, while the existing copy fallback covers Windows. Accepting adds the pattern to a new `RepositoryConfigEdit.addLinkPatterns`, shown in the pending patterns list marked as linked and written on save with the existing preview, so `.shogunai.json` declares the pattern (never the secret) for every clone. Alternative: add the file to the local list. Rejected: the roadmap's direction is declaring once in the repository; the user can still add it locally by hand.

**Keystore references are read from the detected properties files only.** In each detected `local.properties`, `keystore.properties` and `key.properties`, a key whose name, lowercased and without `.`, `_` and `-`, ends with `storefile` names a keystore. An absolute value is left alone (it resolves from any worktree). A relative value is resolved against the properties file's folder and against the repository root, because Gradle scripts use both (`file()` in a module, `rootProject.file()`): if a candidate is an untracked file inside the repository, it's suggested as a keystore; if every candidate falls outside the repository, a warning names the file, the key and the value. A missing keystore inside the repository is ignored. Alternative: parse Gradle scripts to know the real base folder. Rejected: Groovy/Kotlin scripts can't be evaluated reliably, and both candidates cover the usual layouts.

**Secret detection lives next to stack detection.** A `DetectMobileSecretsUseCase(executor, fileManager)` returns `MobileSecretsReport(secrets: List<MobileSecret(path, kind)>, warnings: List<KeystoreReferenceWarning(file, key, value)>)`, with `kind` one of local properties, signing properties, keystore and Firebase configuration. `shogun stacks` and the settings call it alongside `DetectRepositoryStacksUseCase`; it doesn't depend on a stack being detected, because the file names are specific enough on their own.

**Link mode is a second list in `ProjectConfig`.** `linkedSecretFiles: List<String> = emptyList()` holds the entries of `secretFiles` that are linked; an entry in it but not in `secretFiles` is ignored. Alternative: turn `secretFiles` items into objects with a mode. Rejected: earlier versions would fail to read `projects.json` and lose the project, while an extra list is ignored by them (`ignoreUnknownKeys`) and they keep copying. Removing an entry, and the base path migration, apply to both lists. A local entry keeps winning over `.shogunai.json`: a local entry in copy mode is copied even if `link` matches it, one in link mode is linked even if only `copy` matches it.

**A linked folder is one symbolic link.** `ProvisionedFiles` gains `linkedFolders: List<String>`; `applyProvisionedFiles` creates one link at the folder's path pointing to the base folder, after `requireInsideWorktree` on its parent. If the destination already exists as a real folder, it's replaced only when every file under it is one ShogunAi recorded as copied from that folder (the copy-to-link switch); otherwise the operation fails with `WorktreeError.LinkedFolderOccupied(entry)` and nothing is deleted (on creation, the worktree is rolled back like a failed copy). An existing symbolic link at that path is replaced. On `SymbolicLinksNotSupported`, the folder's files are copied and recorded, each reported as copied instead of linked. The reverse switch is handled too: before copying a folder whose destination is a symbolic link to the base folder, that link is removed, so the copy never writes through it into the base repository (any other link there is left to `requireInsideWorktree`, which refuses it). Linking file by file was rejected: it wouldn't show files added to the base folder until the next provisioning, which is the point of linking.

**Patterns in the local list reuse the `copy` selection.** An entry containing `*`, `?` or `[` is a pattern: it's passed to the same `git ls-files --others --ignored -x` expansion as `copy`, so it selects untracked files only, at the path Git reports, and in the entry's mode. It isn't checked for existence (no `SecretFileNotFound` when it matches nothing). The app accepts patterns only relative to the repository (an absolute pattern is refused with a message), and "Move to .shogunai.json" moves a pattern unchanged (it's already a pattern) and a linked entry into `link` instead of `copy`.

**Folder listings report their skipped links.** `FileManager.listFiles` becomes `listTree(directory): DirectoryListing(files, skippedLinks)`, both relative and `/`-separated; symbolic links are still not followed. `ProvisionedFiles` carries the skipped links with their path relative to the repository root, and `ProvisionResult` and `Worktree` expose them as `skippedLinks`. The settings show, under a copied folder entry, how many links it skips, computed with the same listing when the entry is shown.

**A per-worktree record of folder copies.** A new port `ProvisioningRecordStore` reads and writes `<git admin folder>/shogunai-provisioning.json`: `{ "localFolders": { "<entry>": ["<file relative to the entry>", …] } }`. The admin folder lives outside the working tree, so the record is never committed and disappears with the worktree. After copying, the record of every listed copied folder is replaced by the files just copied; entries no longer in the list are dropped from the record without touching their files. Before copying, every recorded file of a still-listed folder that no longer exists in the base folder is deleted from the worktree when it's a regular file there; anything else at that path is left alone. A base folder that doesn't exist at all still fails with `SecretFileNotFound` before anything is deleted, so a moved or unmounted base folder never empties the worktrees. Worktrees provisioned before this change have no record, so nothing is deleted until they've been provisioned once. A failure to write the record is a `SecretCopyFailed`.

**A new drift state for deleted files.** `ProvisionDriftState.DELETED_IN_BASE` is reported for each recorded file of a listed folder that's still in the worktree but gone from the base folder; the CLI prints `deleted in base` and the JSON `deleted-in-base`; `shogun provision --check` keeps exiting with 3 when anything is reported. `ProvisionResult` gains `removed: List<String>`, printed by `shogun provision` and listed in its JSON.

## Risks / Trade-offs

- [A worktree edited its copy of a folder file that was later deleted from the base folder; provisioning deletes it] → the drift check reports it first as deleted in base, deletion only touches files ShogunAi recorded as its own copies, and the user chose this rule over an exact mirror.
- [A linked folder makes secrets writable from every worktree] → link mode is opt-in per entry and the guide repeats the warning already given for `link`.
- [Detection suggests a keystore that isn't a mobile signing key, e.g. a backend's TLS keystore] → it's a suggestion only, shown with its path; linking it is still useful in a worktree.
- [The keystore warning misses a layout where Gradle resolves the path from a third folder] → the warning is advisory; a missing warning never blocks anything.
- [The record and the worktree disagree after a manual edit of the admin folder] → a missing or unreadable record is treated as empty, which only means nothing is deleted.

## Migration Plan

No migration: `linkedSecretFiles` defaults to empty, existing entries keep copying, and the record starts being written on the first creation or provisioning after the upgrade. Rolling back to an earlier version ignores the new field and the record file.
