## Context

`CopyWorktreeLaunchCommandUseCase.invoke` (`domain/usecase/CopyWorktreeLaunchCommandUseCase.kt`) builds the clipboard payload as `"cd '$worktreePath' && ${config.agentLaunchConfig.resolvedCommand()}"`. Single quotes are a valid quoting mechanism in bash, zsh, and PowerShell, but not in `cmd.exe`: there, a leading/trailing `'` is passed through as a literal character in the argument, so `cd 'C:\Users\...\worktree'` tries to enter a path that includes the quote characters and fails. See proposal.md - Why.

## Goals / Non-Goals

**Goals:**
- Make the copied `cd` command work when pasted into `cmd.exe`, PowerShell, bash, or zsh, without asking the user which shell they use.
- Keep the fix scoped to the string built in `CopyWorktreeLaunchCommandUseCase`.

**Non-Goals:**
- Detecting the user's OS or target shell. Not needed once a single quoting style is valid everywhere.
- Handling worktree paths containing a double quote or a `$` character. Worktree paths are filesystem paths generated by the app's own worktree-creation flow (see `worktree-workspace` capability); they aren't expected to contain shell-special characters, and no such case is reported.

## Decisions

### Use double quotes instead of single quotes, with no OS detection

Double quotes are valid quoting for a plain path argument in all four targeted shells (`cmd.exe`, PowerShell, bash, zsh), so swapping the quote character fixes `cmd.exe` without breaking any shell that already worked. This is a one-line change with no new abstraction.

**Alternative considered**: introduce an OS-detection port (mirroring the `ClipboardWriter`/`ShellCommandExecutor` ports in `domain/executor`) and choose single quotes on Unix-likes, double quotes on Windows. Rejected: it adds a new port, a new injected dependency in `AppContainer`, and OS-conditional test setup, all to reproduce a distinction that double quotes make unnecessary — there's no shell in scope where double-quoting a plain path is wrong.

**Alternative considered**: detect the target shell instead of the OS (e.g. respecting `$SHELL`/`COMSPEC`) and tailor the quoting further. Rejected: the app has no way to know which shell the user will paste into (they copy now, paste later, possibly in a different terminal session), so this would be guessing at information the app doesn't have.

## Risks / Trade-offs

- **[Risk] A worktree path containing a `"` or `$` would still break the copied command.** → **Mitigation**: none added here; this is a pre-existing limitation (single quotes had the same class of gap for a literal `'`) and no worktree path with such characters is known to occur given how worktrees are created today.

## Migration Plan

No data migration. Pure string-format change in `CopyWorktreeLaunchCommandUseCase`; rollback is a straight revert of that file and its test.
