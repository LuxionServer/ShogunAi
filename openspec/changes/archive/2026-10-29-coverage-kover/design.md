# Design

## Context

The three modules are plain Kotlin/JVM Gradle projects (`core` with a `testFixtures` source set shared with `cli` and `desktopApp`), tested with `kotlin-test-junit`, and CI runs `./gradlew test` on Linux, macOS and Windows through the reusable `test-suite.yml` (called by `tests.yml` and `release.yml`). There is no coverage tool today.

Baseline measured with Kover 0.9.11 on macOS on `develop` at 8d2e40c1, test fixtures excluded, composables excluded in the desktop app, before this change's tests:

| Module | Lines | Branches |
|---|---|---|
| `core` | 95.4% (412 uncovered) | 76.3% (1,729 uncovered) |
| `cli` | 91.8% (322 uncovered) | 78.6% (664 uncovered) |
| `desktopApp` outside composables | 76.1% (2,558 uncovered) | 62.3% (2,489 uncovered) |

Many uncovered branches are generated by Kotlin rather than written: the bitmask branches of constructors and functions with default arguments, `?.` and `?:` chains, `when` over sealed types, coroutine state machines and serializers. That is why the roadmap's 100% everywhere was turned, by Ciro's decision, into a ratchet.

## Goals / Non-Goals

**Goals:**

- Measure line and branch coverage of every module with one tool and one command.
- 100% of lines in `core` and `cli` at the end of this change.
- A floor for every other figure at today's level, so coverage can't go down, and a written path up to 100%.
- CI fails a pull request that breaks any rule.

**Non-Goals:**

- 100% of branches in `core` and `cli`, and 100% of the desktop app outside its composables. They are later steps in the roadmap.
- Covering composables: the `desktop-e2e-tests` change covers them with end-to-end tests.
- End-to-end tests of the CLI against real Git (`cli-e2e-tests`).
- A coverage badge, a coverage service or pull request comments with coverage diffs.
- Refactoring how the code reads the operating system or the environment: `host-environment` owns that.

## Decisions

### Kover, applied per module

Kover (JetBrains' coverage tool for Kotlin, version 0.9.11) is applied to each module through the version catalog. Its IntelliJ agent understands Kotlin bytecode better than JaCoCo (inline functions, `$default` stubs, data class members), which removes part of the generated branches from the count. Each module has its own `kover { reports { verify { ... } } }` block, so thresholds are per module and a failure names the module. A merged root report was considered and dropped: one total figure would let a well-tested `core` hide an untested `cli`.

### Rules as whole percentages, floored

Ciro chose a minimum percentage over a maximum count of uncovered lines and branches. Kover's bounds are whole percentages, so each floor is today's figure rounded down (for example, 76.3% → 76). `core` and `cli` lines are at 100, which leaves no slack: every new line needs a test. The floors leave under one point of slack, so a change that adds a little untested desktop code may still pass; that is the trade-off accepted with the percentage rule.

### Exclusions are listed in the build scripts

- `testFixtures` is excluded from every module's measurement (it is test code shared between modules, not production code).
- `*$DefaultImpls` classes are excluded from every module: they are bridges the compiler generates so that Java callers can reach an interface's default methods, and no code in ShogunAi calls them.
- In `cli`, `MainKt` is excluded: `main` calls `exitProcess`, and `runShogun` only builds the real adapters (with the real home folder and the real standard input) and hands them to `ShogunCli`, which every command test exercises. The end-to-end tests of the CLI (`cli-e2e-tests`) run it as a process.
- In the desktop app, functions annotated with `@Composable` or `@Preview` and the `ComposableSingletons` classes Compose generates for composable lambdas are excluded.
- Nothing else is excluded. A new exclusion needs its reason in this design or in a later change's.

### Verified on the macOS job

`test-suite.yml` runs `./gradlew koverVerify` after the tests, only in its macOS job. Running it there means `release.yml`, which reuses the suite, also refuses to release a commit below a threshold. Coverage depends on the system the tests run on: some code reacts to the real platform (a read-only file can only be deleted after making it writable on Windows, an unreadable folder can only be prepared with POSIX permissions, symbolic links need privileges on Windows), so the same suite covers slightly different lines on each system. Requiring every system would force tests written per platform for no gain in behavior; verifying on one system keeps a single set of numbers. macOS was chosen over Linux because it is the system ShogunAi is developed on, so `./gradlew koverVerify` on a developer's machine gives exactly the result CI will give. The other jobs still run every test. Code that depends on the operating system is tested by injecting it (`osName` constructor parameters), so Windows and Linux paths are covered on macOS too.

### Tests to reach 100% of lines

The uncovered lines of `core` and `cli` are listed from Kover's XML report and covered class by class with unit tests next to the existing ones, using the existing fakes in `core`'s test fixtures (`FakeShellCommandExecutor`, `FakeFileManager` and the like) and temporary folders for the `Nio*` adapters. A line reached only by a real external tool (Herdr, Orca, `xcrun`, `adb`) is tested through the `ShellCommandExecutor` port with a fake answer, not by running the tool.

### Production changes made to reach the lines

Writing the tests surfaced lines no test could reach. They were dealt with without changing behavior:

- Dead code was removed: `ToolCatalog.multiplexerExecutable` (never called) and default parameter values every caller already passes (`selectCleanup`'s `runningAgents`, `WorktreeFolderRemoval.remove`'s `hasOrcaTerminals`, the trailing parameters of `emulatorJson` and `simulatorJson`).
- Unreachable branches were removed: the `GRADLE_DAEMON` branches of `AcquireWorktreeResourceUseCase`, whose public functions only acquire emulators and simulators (the reservation is now split into `reserveEmulatorPort` and `reserveSimulator`); the `null` branch of the CLI's daemon owner label, always reached through `?.`; and the `else` of the CLI's `withJson`, replaced by a `JsonOutput` interface that each command with JSON output implements.
- Values of private companion objects that only their own class reads are now `private`, so the compiler no longer generates getters nobody calls.
- Seams for failures a test can't otherwise provoke, as constructor or function parameters defaulting to today's behavior: how `NioFileManager` creates a symbolic link, how `LocalFileLock` and `FileAppInstanceLock` take the file lock, and how `ShogunCli` registers its shutdown hook. `launchDetached` in `LocalAndroidSdk` became `internal` to be tested directly.
- `ProcessMavenDaemonSource` reads a log's modification time before its tail, so a log that disappears is handled by the same `null` either way.

Failures that need a file the test can't read (an unreadable folder or settings file) are prepared with POSIX permissions and skipped where the file system has none; they run on the macOS job that verifies coverage.

### How the floors go up

`AGENTS.md` gets the rule: a change that raises a module's figure past a whole percentage raises its floor in the same change; a floor is never lowered. The roadmap keeps the remaining steps (branches of `core` and `cli`, then the desktop app) as items, each a change of its own.

### Thresholds set by this change

Measured on macOS after this change's tests:

| Module | Lines | Branches |
|---|---|---|
| `core` | 100% (rule: 100) | 78.67% (rule: 78) |
| `cli` | 100% (rule: 100) | 83.03% (rule: 83) |
| `desktopApp` outside composables | 76.15% (rule: 76) | 62.27% (rule: 62) |

Bringing in `develop` before the pull request added `desktop-e2e-tests` and `worktree-preflight`. The desktop app's end-to-end tests raised its figures to 83.40% of lines and 65.37% of branches, so its floors went up to 83 and 65; `worktree-preflight` left one line of `core` without a test (a file that exists but can't be opened as one), covered here with a Unix socket file.

## Effect on the changes in flight

Six reliability changes started in parallel from `develop` at 8d2e40c1. Whichever merges after this one has to pass `koverVerify` once it brings in `develop`:

- `host-environment` and `worktree-preflight` add or move production code in `core` and `cli`: every line they add must be covered by a unit test, or their pull request fails. Moving code that is covered today keeps it covered as long as its tests move with it.
- `cli-e2e-tests` adds tests only. Its end-to-end tests run in the `test` task, so they also count towards coverage and can only raise it; if it adds test helpers to `core`'s test fixtures, they are excluded.
- `desktop-e2e-tests` adds tests of composables, which are excluded, and may add non-composable test helpers or production hooks in the desktop app: those count against the desktop floors, which leave less than a point of slack.
- `packaged-smoke-test` works on the release workflow and may also edit `test-suite.yml`; this change only adds a "Verify coverage" step after "Run tests" there, so a conflict is a small merge.
- If one of them merges first, this change brings in `develop` before opening its pull request and re-runs `./gradlew test koverVerify`; any line of `core` or `cli` it added without a test gets a test here, and a desktop floor that no longer holds is lowered only to the figure measured then, with the reason in this design.
- `host-environment` moves how the operating system and the environment are read; the `osName` parameters the tests here inject may move with it, and its tests must keep covering both sides.

## Risks / Trade-offs

- [The `test` task gets slower with the agent attached] → Kover's overhead on these suites is a few seconds; measured locally the full run of the three modules with the reports takes about a minute, within the 10-minute job timeout.
- [Coverage differs between operating systems] → Only the macOS job verifies, with the numbers a developer gets locally; operating-system paths are covered through injected `osName`. A path that only runs natively on Windows or Linux and isn't injectable would go unnoticed by the rule; new code of that kind should take the system as a parameter.
- [Tests written only to touch lines] → Each new test asserts the behavior of the line it covers (a result, an error or a command sent through a port), reviewed like any other test.
- [A whole-percentage floor lets a small amount of untested desktop code in] → Accepted with the percentage rule; the desktop floors go up as the desktop is covered, and lines of `core` and `cli` have no slack.

## Migration Plan

No migration: the build gains the plugin and a task, CI gains the verification. Rolling back is removing `koverVerify` from `test-suite.yml`.
