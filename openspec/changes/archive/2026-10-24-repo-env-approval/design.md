# Design

## Context

See proposal.md - Why. Today:

- `RepositoryTrust` (port) and `JsonRepositoryTrust` (`~/.shogunai/trust.json`, mode 600) approve a repository's `postCreate` argv list by a SHA-256 of its canonical JSON. `PostCreateApproval.decide(repository, commands)` asks the user (CLI prompt, desktop dialog, or `SKIP` where nobody can be asked). `runApprovedPostCreateCommands` (`WorktreeCreation.kt`) checks and asks after the environment has already been prepared.
- `env`/`envFile` are parsed by `RepositoryProvisioningFiles.environmentOf` into `EnvironmentDeclaration`. Names pass `isValidVariableName` and `isReservedVariableName` (a small set plus `LD_`, `DYLD_`, `GIT_`). Values are free text.
- Every consumer of the environment goes through `ResolveWorktreeEnvironmentUseCase`: `PrepareWorktreeEnvironmentUseCase` (reservation plus `WriteEnvironmentFileUseCase`), `shogun env`, `shogun hook session-start`, `OpenWorktreeInTerminalUseCase`, `OpenWorktreeInHerdrUseCase`, `OpenGroupInHerdrUseCase`, the desktop detail pane, and the emulator/simulator/release use cases.
- Provider variables (`GRADLE_OPTS`, `MAVEN_OPTS`, `COMPOSE_PROJECT_NAME`, `XCODE_XCCONFIG_FILE`, `ANDROID_SERIAL`, `IOS_SIMULATOR_UDID`, Compose `portVariables`) are generated by ShogunAi, with values it computes; only the names of `portVariables` come from the repository.
- `ShogunCli.configFor` builds a default `ProjectConfig` for an unregistered repository, so the `SessionStart` hook acts in any repository.

## Goals / Non-Goals

**Goals:**

- One enforcement point for declared variables, so no current or future consumer can deliver them unapproved.
- Existing approvals of repositories that declare no `env`/`envFile` stay valid.
- A backstop that holds even when the user approves without reading: names that change other tools are never accepted.

**Non-Goals:**

- Approving provider variables: their values are computed by ShogunAi, and the repository only picks the names of Compose `portVariables`, which go through the reserved-name check.
- Covering the contents of files the approved commands run, or of the repository's own build scripts: building or running a repository's code is already trusting it.
- Gating `shogun hook herdr` and `shogun hook worktree-create` on registration: they only provision approved configuration, which is enough once declared variables are gated.

## Decisions

### D1. One approval subject per repository

`RepositoryTrust` changes from commands to a `RepositoryApprovalSubject(commands: List<List<String>>, variables: List<Pair<String, String>>, envFile: String?)` (name and declared template text). `isApproved(repository, subject)`, `approve(repository, subject)`, `revoke(repository)`. An empty subject (no commands, variables or `envFile`) counts as approved, so callers don't special-case it.

Digest: when `variables` is empty and `envFile` is null, the digest is exactly today's (`sha256(Json.encodeToString(commands))`), so stored approvals keep working. Otherwise it is the SHA-256 of a canonical JSON object `{"commands": [...], "env": [[name, template], ...], "envFile": ...}` with `env` sorted by name: the order of keys in `.shogunai.json` doesn't change behavior, so reordering them doesn't ask again, while the order of commands does. The stored `Approval` gains `env: Map<String, String> = emptyMap()` and `envFile: String? = null`, decoded with defaults from older files.

`EnvironmentVariable` keeps the declared template text (`source`) next to its parsed parts, so the digest and every prompt use exactly what the file says.

Alternatives: separate approvals for commands and variables (rejected by the user: more prompts, more code); a digest of the whole `.shogunai.json` (would ask again for harmless edits like `copy` patterns, and invalidate every existing approval).

### D2. Gate declared variables inside the resolver

`ResolveWorktreeEnvironmentUseCase` takes a `RepositoryTrust` and, after reading the provisioning, builds the subject and checks it. When not approved it treats the declaration as empty (no declared port requests, no rendered variables, no precedence over providers) and returns `WorktreeEnvironment(awaitingApproval = <declared names>, declarationApproved = false, ...)`. `WriteEnvironmentFileUseCase` writes nothing when `declarationApproved` is false, which also covers an `envFile` declared without `env`.

The constructor's trust defaults to `RepositoryTrust.NONE` (nothing approved): forgetting to wire it fails closed. Tests that need declared variables use `FakeRepositoryTrust` with an approval.

Alternative: check trust in each consumer (hook, terminal, Herdr, env, detail pane). Rejected: six call sites today, and the next consumer would be one more chance to forget it.

### D3. Ask before preparing the environment

`PostCreateApproval` becomes `RepositoryApproval` with `decide(repository, subject): ApprovalDecision` (`APPROVE`, `SKIP`); `SKIP` stays as the non-interactive default. The creation and provisioning flow becomes: add worktree, copy/link files, `settleApproval` (approved already, or ask; on `APPROVE` store the approval), prepare the environment (the resolver now sees the result), then run the commands only if approved. `Worktree` gains `skippedVariables: List<String>` next to `skippedPostCreateCommands`; the CLI notes and JSON (`skippedVariables`) and the desktop result read them.

The rename touches the desktop dialog (`DialogPostCreateApproval` → `DialogRepositoryApproval`), `CreateGroupUseCase`, `CreateWorktree*UseCase`, `ProvisionWorktreeUseCase`, and the CLI wiring; it keeps "post-creation" out of a type that now approves more.

### D4. Reserved names: broad set, case-insensitive

`isReservedVariableName` compares `name.uppercase()` against exact names, prefixes and suffixes, kept in `WorktreeEnvironment.kt`:

- Exact: the current set, plus `USER`, `LOGNAME`, `TMPDIR`, `TMP`, `TEMP`, `PS1`, `PS2`, `PS4`, `PROMPT`, `RPROMPT`, `SHELLOPTS`, `BASHOPTS`, `CDPATH`, `FPATH`, `HISTFILE`, `INPUTRC`, `PAGER`, `MANPAGER`, `EDITOR`, `VISUAL`, `BROWSER`, `SUDO_ASKPASS`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `GOFLAGS`, `GOPROXY`, `GOPATH`, `GOROOT`, `GOBIN`, `GOENV`, `GOTOOLCHAIN`, `GOSUMDB`, `GONOSUMDB`, `GOPRIVATE`, `GONOPROXY`, `GOINSECURE`, `GOWORK`, `GOCACHE`, `GOMODCACHE`, `RUSTFLAGS`, `RUSTDOCFLAGS`, `CC`, `CXX`, `CPP`, `LD`, `AR`, `AS`, `CFLAGS`, `CXXFLAGS`, `CPPFLAGS`, `LDFLAGS`, `MAKEFLAGS`, `MAKE`, `PKG_CONFIG_PATH`, `MAVEN_ARGS`, `KUBECONFIG`, `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE`, `CLOUDSDK_CONFIG`, `AZURE_CONFIG_DIR`, `DBUS_SESSION_BUS_ADDRESS`, `OPENAI_BASE_URL`.
- Prefixes: `LD_`, `DYLD_`, `GIT_`, `XDG_`, `LESS`, `SSH_`, `NODE_` (except `NODE_ENV`), `NPM_CONFIG_`, `YARN_`, `PNPM_`, `BUN_`, `PIP_`, `PYTHON`, `UV_`, `POETRY_`, `CONDA`, `GEM_`, `BUNDLE_`, `RUBY`, `PERL`, `CARGO_`, `RUSTC`, `RUSTUP_`, `CMAKE_`, `CCACHE_`, `DOCKER_`, `GH_`, `ANTHROPIC_`, `CLAUDE_`, `CODEX_`, `HERDR_`, `SHOGUNAI_`.
- Suffixes: `_PROXY`, `_OPTS`, `_HOME`.

The check applies where names come from the repository (`env` and Compose `portVariables`); provider-generated names don't go through it. Provider names that become reserved (`GRADLE_OPTS`, `MAVEN_OPTS`) can no longer be overridden from `env`, which only took the provider's place anyway. The error keeps `RepositoryConfigIssue.ReservedVariableName` and its message names the variable; the desktop editor reuses the same function.

Alternative: an allowlist (a project prefix, or provider names only). Rejected by the user: it breaks ordinary configurations (`PORT`, `DATABASE_URL`, `VITE_API_URL`). The broad denylist is a backstop; the approval is the gate.

### D5. Characters in templates and `envFile`

`parseEnvironmentVariable` rejects a template containing any character of Unicode category Cc (controls, including `\n`, `\r`, `\t`, ESC) or Cf (format: bidirectional controls, zero-width characters), or U+2028/U+2029, with a new `RepositoryConfigIssue.InvalidVariableValue` naming the variable. `envFile` gets the same rule in `RepositoryProvisioningFiles` and `RepositoryConfigRules.isInsideWorktree`'s callers in the desktop editor. Because of this, every prompt that prints a template or `envFile` shows exactly what will apply.

### D6. SessionStart hook

`hookSessionStart` looks up the repository in `projectRepository` (same `sameDirectory` comparison as `configFor`). Not registered: it prints the workflow rules built from a `WorkflowContext` that doesn't read `.shogunai.json` (no provider rules), resolves no environment and writes nothing to `CLAUDE_ENV_FILE`. Registered: as today, but the context line names the variables without values (`ShogunAi environment of worktree TASK-123: PORT, API_URL`), and when `awaitingApproval` isn't empty it adds a line naming them as awaiting the user's approval with `shogun trust`, telling the agent to ask the user rather than approve them itself.

`configFor` keeps building a default config for explicit commands (`shogun new`, `shogun trust`, `shogun env`): the user runs them on purpose, and the approval applies there too.

### D7. CLI and desktop surfaces

- `shogun trust` prints commands, then `Environment variables declared by <repo>:` with `NAME = template` lines, then `Environment file: <path>`; asks once. `trustJson` adds `env` (list of `{name, template}`) and `envFile`. "Nothing to approve" only when the subject is empty.
- The CLI approval prompt during `new`/`provision` prints the same block before preparing the environment. The skipped note names the skipped variables and `shogun trust`. `shogun env` prints the awaiting note on standard error.
- Desktop: the approval dialog lists commands, variables and the environment file. Project settings' approval row covers the subject; saving the environment approves the new subject only when the old one was approved or declares no commands (the settings save path computes both subjects around the write). The detail pane lists `awaitingApproval` names without values.

## Risks / Trade-offs

- [Users of repositories with `env` lose their variables after upgrading until they approve] → the hook, `shogun env`, creation notes and the desktop detail all say which variables await approval and how to approve; the docs and release notes explain it.
- [A configuration using a newly reserved name becomes invalid] → the error names the variable and says it is reserved; the docs list the reserved families. Real-world names checked against the list: `PORT`, `DATABASE_URL`, `NODE_ENV`, `VITE_*`, `NEXT_PUBLIC_*`, `ANDROID_SERIAL`, `API_URL` stay valid.
- [An agent could run `shogun trust --yes` itself after reading the awaiting note] → the note tells it to ask the user; the command is visible in the agent's transcript and subject to the agent's own permission prompts. A prompt-injected agent with shell access can already do worse than approve variables.
- [The user approves without reading] → reserved names can't be approved, and values can't hide text with control characters.
- [Reading `trust.json` on every resolve] → one small file read per resolve; the resolver already reads `.shogunai.json` each time.

## Migration Plan

- `trust.json` stays readable by older versions (new fields are ignored with `ignoreUnknownKeys`) and older files are read with defaults, so downgrading keeps command approvals.
- Repositories without `env`/`envFile` need nothing. Repositories with them need one approval, from `shogun trust` or the desktop app.
- Rollback: reverting the release restores the old behavior; approvals stored by the new version for subjects with variables simply don't match old digests, so the old version asks again for their commands.
