# Command-line tool

The `shogun` command runs ShogunAi's worktree operations from a terminal, a script or an agent hook, without opening the desktop window. It lives in the **`cli`** module (`cli/src/main/kotlin/app/luxion/shogunai/cli`) and calls the same `core` use cases as the app, so a worktree created or cleaned from the command line ends up exactly as if the app had done it.

## Commands

What each command does, its options and its output are in the [command-line reference](../guide/cli.md). This table maps each command to the `core` code it runs and notes the details that only matter when changing it.

| Command | Runs | Implementation notes |
|---|---|---|
| `new` | `ResolveStartPointUseCase` and `ResolveBaseBranchUseCase` on the same ref, then `CreateWorktreeUseCase` or `CreateWorktreeFromBranchUseCase`, with `PrepareWorktreeEnvironmentUseCase` and `WriteEnvironmentFileUseCase` as the environment preparer | Without `--from`, the start point is `HEAD` resolved in the working directory, so a worktree created from a linked worktree branches from that worktree, as `git worktree add -b` does. An unknown ref fails before anything is created. |
| `provision` | `ProvisionWorktreeUseCase` | |
| `status` | `ListWorktreesUseCase`, `ResolveMainBranchUseCase`, `ReadWorktreeStatusUseCase`, `classifyOrigin`, `ReadBaseBranchesUseCase` | The JSON of `--json` is built in `StatusJson.kt`; its field names are a contract, see the [CLI guide](../guide/cli.md#status-json). Failing to read the bases leaves every `base` `null`. The main branch, the agents, the desktop turn and the bases are read concurrently, then the worktree statuses at most 8 at a time, collected in listing order so the output doesn't depend on which read ends first. |
| `base` | `findWorktreeTarget` (or the worktree containing the current directory), `ReadBaseBranchesUseCase`, `SetBaseBranchUseCase` | Unlike `remove`, the target may be the main checkout. |
| `clean` | `selectCleanupCandidates`, `CleanUpWorktreesUseCase`, `CloseHerdrWorkspacesUseCase`, and per option `StopGradleDaemonsUseCase`, `StopWorktreeEmulatorUseCase`, `DeleteSimulatorsUseCase`, `DeleteOrphanedDerivedDataUseCase` | Whatever removal deletes is read first: the Gradle daemons (for `idleDaemonsOfRemovedWorktrees`), the running emulators' serials (`ReadEmulatorStatesUseCase`, then `StopWorktreeEmulatorUseCase.stopSerials`), the simulators' UDIDs and the orphaned DerivedData. Orphaned simulators are looked for again after removing, so the simulator of a worktree whose folder was already gone is caught as an orphan; with only orphans the command still runs. A failed daemon stop, emulator stop or Herdr close goes to standard error without changing the exit code; a DerivedData folder that can't be deleted exits with `1`. |
| `gradle`, `gradle stop` | `ListGradleDaemonsUseCase`, `CheckGradleBuildCacheUseCase`, `StopGradleDaemonsUseCase` | Works outside a repository. Kotlin daemons are kept while a Gradle build runs. |
| `pool status`, `pool trim` | `ReadResourcePoolUseCase`, `TrimGradleDaemonsUseCase` | `status` reads the three pools against the limits of the capacity profile; `trim` stops idle Gradle daemons over the limit. Both accept `--json` (`poolJson`, `poolTrimJson`). |
| `project add`, `project list`, `project remove` | `RegisterProjectUseCase`, `UnregisterProjectUseCase`, `ProjectRepository` | `add` builds the project with `newProject`, the same defaults `ProjectConfigViewModel.chooseFolder` uses (`projectDefaultsFor`), and only calls `save` for a repository with no project, compared by canonical path, so an existing project is never rewritten. `remove` matches by canonical path and, when the folder is gone, by the stored path. The JSON of `--json` is built in `CommandJson.kt` (`projectJson`, `projectListJson`). |
| `app` | `ResolveRepositoryUseCase`, `RegisterProjectUseCase`, `AppInstanceLock`, `AppRequestChannel`, `AppLauncher` | Registers the repository, leaves an `AppRequest` and launches the app only when nobody holds the app lock. See [Reaching the desktop app](#reaching-the-desktop-app). |
| `xcode`, `xcode clean` | `ListDerivedDataUseCase`, `DeleteOrphanedDerivedDataUseCase` | Without the provider or off macOS it exits with `0`. |
| `env` | `ResolveWorktreeEnvironmentUseCase` (reserving), `formatEnvironment` | Reserves declared ports only; on-demand reservations (the emulator's port, the simulator) are read, never acquired. |
| `emulator` | `StartWorktreeEmulatorUseCase`, `StopWorktreeEmulatorUseCase`, `ReadEmulatorStatesUseCase` | `start` acquires the emulator through `AcquireWorktreeResourceUseCase` with the limits of the machine's capacity profile, prints what it released on standard error and the `export ANDROID_SERIAL=…` line on every start (it also renews the lease). With `--wait` it passes a `DeviceWait` whose progress callback prints a line on standard error only when it changes, and prints `waited <time>` after a real wait (`waited` in `--json`). `status` never reserves a port and prints `not acquired` before the first start, followed by `(released for <worktree> at <time>)` when `ReadReleaseRecordUseCase` finds a release record (`releasedFor` in `--json`). Without the provider: `EmulatorProviderNotDeclared`. |
| `headless` | `StartHeadlessAppUseCase`, `StopHeadlessAppUseCase`, `ReadHeadlessAppUseCase`, `CaptureHeadlessAppUseCase` | The worktree is the top level of the path's Git checkout, registered as a project or not. `.shogunai.json` is read from the worktree itself. The ports `HeadlessAppLauncher` (`GradleHeadlessAppLauncher`: `gradlew <module>:hotRunAsync` with an init script) and `AppWindowService` (`MacAppWindowService`: a JavaScript for Automation helper and `screencapture`) are injected, so tests use fakes. A denied hide is a warning on standard error, not a failure. `remove`, `clean` and `hook worktree-remove` pass `StopHeadlessAppUseCase` to the removal, which stops the app before deleting the folder. |
| `desktop` | `AcquireDesktopTurnUseCase`, `ReleaseDesktopTurnUseCase`, `ReadDesktopTurnUseCase` | `acquire` and `release` act on the worktree that is the top level of the path's Git checkout; `status` needs no worktree. The `DesktopTurnStore` (`NioDesktopTurnStore`), the wait queue and the clock and pause are injected, so tests wait without sleeping. `--wait` and `--wait-timeout` are parsed like the device commands'. `status` reads the turn once to add `desktop` to each worktree, `hook agent-state` releases it on `Stop` and `SessionEnd`, and `remove`, `clean` and `hook worktree-remove` pass `ReleaseDesktopTurnUseCase` to the removal. |
| `simulator` | `StartWorktreeSimulatorUseCase`, `StopWorktreeSimulatorUseCase`, `ReadSimulatorStatesUseCase`, `KmpTestWiring` | `start` acquires (creates) the simulator the same way and prints `export IOS_SIMULATOR_UDID=…` when it just did. `status` never creates a simulator and prints `not acquired` before the first start. Without the provider: `IosSimulatorProviderNotDeclared`; off macOS: `IosSimulatorsNotSupported`. |
| `simulator gradle-init` | `KmpTestWiring` | `install` asks on standard input (`readInput`) unless `--yes`. |
| `hook worktree-create` | `CreateWorktreeUseCase`, or the existing worktree | Reads `name` and `cwd` from the hook's JSON and records the branch of `cwd`'s `HEAD` as the base; without a project the worktree goes to `<repo>/.claude/worktrees`. The path must be the only line on standard output. |
| `hook worktree-remove` | `RemoveWorktreeUseCase` (forced), `DeleteMergedBranchUseCase`, `CloseHerdrWorkspacesUseCase` | Forcing the removal is what Claude Code would do without the hook. |
| `hook session-start` | `ResolveWorktreeEnvironmentUseCase` | Only a repository registered as a project (`ProjectRepository`) gets its environment resolved and delivered; elsewhere it prints the workflow rules built without reading `.shogunai.json`. The context names the variables without values, and those awaiting approval separately. `CLAUDE_ENV_FILE` is read through an injected environment lookup. An unreadable `.shogunai.json` exits with `1` before writing. It reserves nothing: for a worktree without an emulator or simulator the context line says how to acquire it. |
| `hook agent-state` | `AgentSessionStore` (`FileAgentSessionStore`) | Maps `UserPromptSubmit`, `Notification` (`idle_prompt` is done, `auth_success` is ignored, anything else is blocked), `Stop` and `SessionEnd` to a record of the worktree containing the hook's `cwd`. The session's `pid` is the first `claude` ancestor of the process (`ProcessHandle`), injected as `agentProcessId`. On a working state it also calls `RenewWorktreeLeasesUseCase` for the worktree. After a valid input it always exits with `0`; every failure is swallowed so the hook never blocks Claude Code. |
| `hooks` | `ClaudeCodeHooks` | Previews first (`previewInstall` / `previewUninstall`), asks through `readAnswer` unless `--yes`, then writes. `CLAUDE_CONFIG_DIR` comes from the injected environment lookup. |
| `hook herdr` | `ProvisionWorktreeUseCase` on `worktree.created`, `DeleteMergedBranchUseCase` on `worktree.removed` | The event comes from `HERDR_PLUGIN_EVENT` and `HERDR_PLUGIN_EVENT_JSON`. On `worktree.removed` the repository comes from `data.workspace.worktree.repo_root`, or else from the project whose worktrees folder contains the path, and Herdr is never called. On `worktree.created` outside the project's worktrees folder it runs `$HERDR_BIN_PATH notification show` (`herdr` when unset). Missing or invalid variables exit with `2`. |
| `help`, `version` | | `version` prints `BuildInfo.VERSION`, the same as the app's. |

Errors are printed from the `WorktreeError` message. The hook commands receive standard input through `ShogunCli`'s `readInput`, so tests pass the JSON directly.

## Repository and project

Every command starts from a directory (the current one, or the path given to `provision`):

1. `ResolveRepositoryUseCase` finds the base repository with `git rev-parse --git-common-dir`, so it works from the main worktree, any subfolder or a linked worktree.
2. The project is the one in `~/.shogunai/projects.json` whose base repository path is the same directory, compared by canonical path (so `/tmp/…` and `/private/tmp/…` on macOS match). It provides the worktrees folder, the local files and the main branch.
3. Without a project, the CLI uses a configuration with no local files and a detected main branch. Only `new` needs a worktrees folder; it asks for `--worktrees-root <dir>` (relative paths are resolved against the current directory).

## Structure

- `CliCommand.kt` — `parseArguments(args)` turns the arguments into a sealed `CliCommand` or a usage error. Hand-written: a dozen commands with about twenty options, each with its own small rules (`--from` not with `--branch`, `--avd` only with `start`, aliases such as `-y`), don't justify a parsing library and its startup cost.
- `ShogunCli.kt` — `ShogunCli(ports…, workingDirectory, out, err).run(args): Int` executes a command. It receives the ports and the output streams, so `ShogunCliTest` drives every command with `core`'s test fixtures and string buffers.
- `Main.kt` — `main` and `runShogun(args)` build `ShogunCli` with the real implementations (`ProcessBuilderShellCommandExecutor`, `NioFileManager`, `JsonProjectRepository`, `RepositoryProvisioningFiles`, `ProcessGradleDaemonSource`, `NioEnvironmentStateStore`, `SocketPortProbe`, `JsonResourceLimitsRepository`, `JvmMachineCapacity`, `LocalAndroidSdk`, `SimctlAppleSimulators`, `FileKmpTestWiring`, `HerdrConfigFile`, `MacDerivedDataSource`, `NioProvisioningRecordStore`; `ShogunCli` defaults its `HerdrClient` to `CliHerdrClient`), and resolves environments through `MachineProviderContributions`, which reads a repository's simulator settings from its project.

The module applies Gradle's `application` plugin, so `./gradlew :cli:run --args="status"` runs it during development and `:cli:distZip` builds the standalone zip.

## Reaching the desktop app

`shogun app` runs in a different process from a running app, so the order travels through two things in `~/.shogunai/`, both new and ignored by versions that don't know them:

- **`app.lock`**: the running app holds an exclusive lock on it for its whole life (`FileAppInstanceLock`). The CLI probes it with `tryLock`: if it gets the lock nobody is running. The operating system releases the lock when the process dies, so a crash leaves nothing stale.
- **`app-requests/`**: one JSON file per request (`AppRequest`: `version`, `createdAt`, `action`, `projectId`, `settings`), written through a temporary file and an atomic move (`FileAppRequestChannel`). The actions are `open-app` and `open-project`.

The app polls the folder about every 500 ms from `Main.kt` once it owns the lock, oldest request first, and hands each one to `AppRequestHandler`, which refreshes the project list, brings the window forward and navigates through `ShellViewModel` (`selectProject` or `editProject`), so the unsaved-changes guard applies and a destination that is already open is left alone. Requests that are malformed, of an unknown version or action, name a missing project or are older than a minute are deleted without effect.

When nobody holds the lock the CLI leaves the request first and then launches the app (`DesktopAppLauncher`): on macOS `open <bundle>`, on Windows and Linux the launcher executable, resolved from the CLI's own path. A command whose executable isn't the app's launcher (`java`, the standalone zip) fails with `AppNotAvailable` before registering or writing anything. The reasoning and the alternatives (socket, `shogunai://` URL scheme) are in the `cli-app-projects` change's `design.md`.

## How it's shipped

The packaged desktop app has a jlink runtime without a `java` binary, so the CLI can't be started by a script reusing it. Instead, **the app's own launcher is the command**: `desktopApp`'s `main(args)` calls `runShogun` and exits when it receives arguments (ignoring macOS's legacy `-psn_…` argument), and opens the window otherwise. The CLI path never loads AWT or Compose, so no window or Dock icon appears, and it starts in about a tenth of a second.

| Platform | How `shogun` is installed |
|---|---|
| macOS (Homebrew) | The Cask links `ShogunAi.app/Contents/MacOS/ShogunAi` as `shogun`. |
| Linux (`.deb`) | The launcher is `/opt/shogunai/bin/ShogunAi`; link it as `shogun` by hand ([Installation](../guide/installation.md#the-shogun-command) shows how). |
| Windows, or anywhere with Java 21+ | `shogun-<version>.zip` from the release: `bin/shogun` and `bin/shogun.bat`. The Windows `.msi` launcher has no console, so it can't print. |

The reasoning and the startup measurements are in the `shogun-cli` change's `design.md` (`openspec/changes/archive/`).
